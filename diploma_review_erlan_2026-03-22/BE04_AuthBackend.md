# BE04: Авторизация Backend

## Оценка: 3/10

## Чеклист

- [x] Регистрация (создание пользователя)
- [x] Хеширование паролей (bcrypt)
- [ ] Логин (проверка credentials, генерация JWT)
- [ ] JWT-токен с payload (userId, role и т.д.)
- [ ] Секрет JWT вынесен в env-переменные
- [ ] Проверка токена в middleware
- [ ] Эндпоинт получения текущего пользователя (me/profile)
- [ ] Роли пользователей или refresh token (для 9+)

## Что реализовано хорошо

- Хеширование паролей через `pre('save')` хук в модели User с использованием bcrypt (salt rounds = 10) — корректный и безопасный подход
- Метод `comparePassword()` вынесен в модель как instance method — хорошая инкапсуляция
- Проверка на существование пользователя при регистрации по email
- Смена пароля (`changePassword`) с проверкой текущего пароля перед обновлением
- Поле `role` в модели User с enum-валидацией (`'user' | 'admin'`) — структура для ролей заложена
- Пароль исключается из ответов через `.select("-password")`

## Что нужно улучшить

- **JWT полностью отсутствует** — пакет `jsonwebtoken` не установлен, токены не генерируются и не возвращаются при логине/регистрации. Эндпоинт `login` просто возвращает данные пользователя без токена, что делает невозможной stateless-авторизацию
- **Нет auth middleware** — ни один маршрут не защищён. Административные эндпоинты (`/all`, `/:id/reset-password`, `/:id/role`) доступны любому без аутентификации
- **Нет эндпоинта `/me` или `/profile`** — текущий пользователь получается по `/:id`, что требует знания ID и не привязано к сессии/токену
- **Роли не проверяются** — несмотря на наличие поля `role`, нет middleware для проверки прав доступа (например, только admin может менять роли или сбрасывать пароли)
- **Критическая уязвимость**: любой может вызвать `PUT /:id/role` и назначить себе роль admin, или `POST /:id/reset-password` для сброса чужого пароля
- Нет валидации входных данных при регистрации (минимальная длина пароля, формат email)
