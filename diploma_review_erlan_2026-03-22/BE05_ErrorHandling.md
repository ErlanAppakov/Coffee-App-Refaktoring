# BE05: Обработка ошибок

## Оценка: 5/10

## Чеклист

- [x] try/catch в контроллерах (или async wrapper)
- [x] Правильные статус-коды (400, 401, 403, 404, 500)
- [x] Информативные сообщения об ошибках
- [x] Единый формат ошибок ({ message, error, ... })
- [ ] Глобальный error handler middleware
- [ ] Обработка ошибок Mongoose (ValidationError, CastError)
- [ ] Не отдаётся stack trace в production

## Что реализовано хорошо

- **100% покрытие try/catch**: каждый контроллер (6 файлов, ~25 функций) оборачивает тело в try/catch — сервер не упадёт при необработанном исключении
- **Разнообразие статус-кодов**: используются 201 (создание ресурса в `register`, `createCatalog`, `createFAQ`, `createHero`), 400 (валидация: дубль email, отсутствие пароля, невалидная роль, превышение размера аватара, пустой массив товаров), 401 (неверные credentials, неверный текущий пароль), 404 (не найден: пользователь, категория, блог, FAQ, каталог, hero), 500 (серверные ошибки)
- **Единый формат ответа**: все ошибки возвращаются в формате `{ error: "сообщение" }` — консистентно во всех контроллерах
- **Информативные сообщения**: ошибки содержат конкретные описания на русском языке (`"Пользователь с таким email уже существует"`, `"Роль должна быть 'user' или 'admin'"`, `"Товары обязательны"`)
- **Хорошая валидация в userController**: проверка обязательных полей, валидация роли, проверка размера аватара, проверка длины пароля

## Что нужно улучшить

- **Глобальный error handler содержит баг** (`index.ts:38-41`): параметр Response назван `_res`, но в теле используется `res` — переменная, не определённая в данной области видимости. В результате глобальный обработчик ошибок не работает при реальном вызове:
  ```typescript
  app.use((err: Error, _req: Request, _res: Response, _next: NextFunction) => {
    console.error(err.stack);
    res.status(500).json({ error: 'Something went wrong!' }); // res не определён!
  });
  ```
- **Нет обработки специфичных ошибок Mongoose**: `ValidationError` (ошибки валидации модели) и `CastError` (невалидный ObjectId) попадают в общий catch и возвращаются как 500 вместо 400. Например, запрос `GET /api/users/invalid-id` бросит CastError и вернёт 500 вместо 400
- **`error.message` отдаётся клиенту напрямую** в catch-блоках (`res.status(500).json({ error: error.message })`): в production это может раскрывать внутренние детали реализации (имена коллекций, структуру запросов Mongoose, пути файловой системы)
- **Нет async wrapper / utility**: try/catch дублируется вручную в каждой из ~25 функций — много boilerplate-кода. Стоит создать `asyncHandler` обёртку
- **Не используется статус 403 (Forbidden)**: хотя есть роли user/admin, нигде нет проверки авторизации с возвратом 403 — любой пользователь может выполнять admin-операции
- **Нет кастомных классов ошибок**: все ошибки формируются вручную в каждом месте, что затрудняет поддержку единообразия
- **Нет логирования ошибок**: в catch-блоках ошибки не логируются (кроме одного `console.error` в `updateUser`), что усложняет отладку в production
